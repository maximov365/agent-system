## Findings and recommended work

### F1 — Touch journeys actually send mouse input

**Confirmed defect; fix first.** `tools/visual/run.mjs:208` implements `tap` with
`page.mouse.click`, even when the browser context has touch enabled. A test that
claims to exercise mobile input can miss broken touch-specific controls.

An isolated page recorded the input type and touch-start count:

| Input | pointerType | touchStarts |
|---|---|---|
| Current framework `tap` | mouse | 0 |
| Playwright `page.touchscreen.tap` positive control | touch | 1 |

The framework journey expecting touch correctly failed with
`Probe pointerType: expected touch, got mouse`. The ordinary regression suite
passes because it does not cover this action. Reproduction:
`.agent/audit/2026-10-09/reproduce-touch.mjs`; full comparison and trace are retained.

Use the actual touchscreen API, validate coordinates/context, and add regression
coverage for touch-only controls and unsupported desktop use. Acceptance: a
touch-specific fixture passes, a deliberately broken touch handler fails, and
ordinary mouse/keyboard journeys retain their behavior. This is a framework
tooling fix; no application or game feature is needed. The expected event behavior
is documented in [Playwright Touchscreen](https://playwright.dev/docs/api/class-touchscreen).

### F2 — Deployed instructions reference absent framework history

**Confirmed packaging/reference defect.** `docs/EVOLUTION_LOG.md` is absent from
every downstream and is not a deployment/seed entry. References occur in
`agents/spec-reviewer.md:205`, `docs/MAST_MAPPING.md:17`, and twice in
`agents/discovery-modes/ai-landscape.md`. Copying the framework's entire historical
log into every project would give projects the wrong history.

Replace method/evidence references with relevant primary sources or self-contained
guidance. Treat a project's research log as optional and create a minimal
project-owned log when research is recorded. Qualify or remove the old CoVe
percentage: a factual-reasoning benchmark is not evidence of improvement in our
code reviews. Preserve historical entries as history.

Improve `audit.py:210` alongside the repair: attach project identity to findings,
group duplicate occurrences, and check supported local Markdown links/skill
references. Its current backtick-path scan is narrower than the success message
"All file references ... are valid" implies. Acceptance: a fresh deployment has
no broken active references; an intentionally broken skill link is caught; reports
identify the affected project without copying framework history into it.

### F3 — Readiness tooling is deployed but project adoption is incomplete

**Confirmed configuration gap.** None of the 18 project profiles declares the
new `readiness` section. The tool can inspect executable presence, but cannot
verify undeclared prerequisites or launch contracts. One project has no profile;
eight more currently declare no runnable checks.

Populate project-owned requirements and launch/check contracts from each actual
application. Start with projects in active development; retain an explicit
not-applicable/unavailable result for projects without a runnable product. Do not
invent universal launch commands. Acceptance for each runnable project: documented
setup, verified launch identity, a successful representative interaction, and
actionable output for one missing prerequisite. Never count an HTTP 200 response
alone as a functional or visual pass.

Add an optional, bounded host-capability diagnostic later: installed runtime,
project skill discovery/errors, observed browser/media tools, and unknown model or
service-tier fields. Keep plain doctor cheap and offline. Use verified host
interfaces, with a portable unavailable result elsewhere. The actual skill probe
in this audit is a useful basis, not evidence that all host capabilities work.

### F4 — CI uses an operating-system alias with an imminent change

**Compatibility risk with a dated upstream trigger; no current failure.** Both
jobs in `.github/workflows/agent-quality.yml` use `ubuntu-latest`. GitHub announced
that its migration to Ubuntu 26.04 begins **October 19** and is expected to finish
**November 19, 2026**. This announcement predates our last audit but matters now.
[Official runner-images notice](https://github.com/actions/runner-images/issues/14748).

Pin the currently validated OS after checking the successful CI runner record;
test Ubuntu 26.04 separately before adopting it. Include Python 3.10/3.14 and
browser dependency installation in that comparison. Acceptance: fresh successful
CI on the explicit baseline, a recorded 26.04 result, and an intentional switch
with a reversible workflow change. No new CI run was triggered in this audit.

### F5 — Motion evidence and design-effect measurement need completion

**Evidence gap, not proof that the design skills are ineffective.** The release
already supplied `DESIGN_CRAFT`, project brand guidance, two design skills, asset
validation, and a visual-comparison protocol. The new multi-file/UI model runs and
visual A/B comparison have not been executed. The editorial and game comparison
rows still need exact frozen fixtures before use.

The browser tool already supports optional video. It is pinned to Playwright
1.62.1, has no video frame-rate setting, and does not index recordings in its HTML
report. Default reduced motion and animation-disabled screenshots are useful for
stable images but insufficient for assessing transitions or game feel.

[Playwright 1.64](https://playwright.dev/docs/release-notes#version-164) adds custom
video frame rates, including the library `recordVideo` option, and changes video
encoding. A controlled upgrade can support better motion review. Firefox/WebKit
capture remains limited to 25 fps; a requested recording rate does not establish
actual app frame performance. Experimental WebMCP support is not required for this
framework and should wait for a real use case.

Acceptance: preserve existing regression behavior; record and link normal-motion
video alongside reduced-motion checks; cover actual touch and keyboard; retain
measured frame-time evidence separately. Then run frozen workspace, editorial and
game-menu/HUD comparisons with equal content/tools/budgets and neutral A/B labels.
Record reviewer identity and independence, functional failures, elapsed time,
usage, viewed artifacts and concrete design observations. Publish failures and
ties as well as wins. Keep fixtures/assets outside downstream deployment.

`evals/run_paired.py` also needs requested/observed service-tier and relevant skill
metadata before speed-tier comparisons. It already records requested model and
leaves unresolved identity null. Preserve that distinction rather than inferring
observations from requested settings.

## Avoid unnecessary additions

- Do not add more agent roles, a compulsory model router, or a second orchestration
  framework without a recurring measured gap.
- Do not install a full external design bundle merely to duplicate our methods.
  The reviewed [Impeccable upstream](https://github.com/pbakaus/impeccable) includes
  an engine download and host hooks; our adapted methods need neither.
- Keep native image generation and project-owned asset contracts. API image
  controls do not imply that the native image tool exposes identical parameters.
- Preserve Astra, explicit optional speed tiers, scoped skill loading, and the
  separation between framework tools and example applications.
